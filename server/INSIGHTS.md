## What Doesn't Work

- **2026-07-15** — `OpenRouterProvider.complete()` (`reviewer-core/src/llm/openrouter.ts`) is an intentional always-throwing stub — only `completeStructured()` is implemented. A module that calls `.complete(...)` passes every unit/integration test cleanly (`MockLLMProvider` implements both methods fine) and only fails against the REAL provider at request time. Caught building Blast Radius's summary step: `blast/summarize.ts` originally used `.complete(...)`, worked in all tests, then threw `"OpenRouterProvider only implements completeStructured"` as a live HTTP 500 the first time a real "Recompute" click hit OpenRouter. Fix: mirror `intent/extract.ts`'s pattern — always `llm.completeStructured({model, schema, schemaName, messages, ...})`, never `.complete()`, for any new LLM-calling module. Mocked tests cannot catch this class of bug; only a live/production-adapter check can. Evidence: `reviewer-core/src/llm/openrouter.ts`, `server/src/modules/blast/summarize.ts`.
- **2026-06-19** — Adding a NEW required field to a persisted document contract breaks reading old rows: `run_traces.trace` is stored JSON, so making `RunStats.cost_usd` `.nullable()` (key required) throws in `RunTrace.parse` on traces written before the field existed. Use `.nullish()` for fields added to already-persisted contracts. Evidence: `src/vendor/shared/contracts/trace.ts`.
- **2026-07-12** — A naive grep for `container.llm|completeStructured|.complete(` to prove a module makes zero LLM calls is fragile — it can false-positive on those identifiers merely appearing in an explanatory doc comment (hit directly while building Smart Diff: a comment explaining "no LLM call" spelled out the literal grepped terms). Verify by reading control flow, not just grepping, or reword nearby prose to avoid the literal identifiers. Evidence: `src/modules/smart-diff/service.ts`, `routes.ts`.

- **2026-07-18** — A prompt rule about PROSE FORMATTING is unenforceable against a cheap model; the same requirement expressed as a TYPED FIELD in the `completeStructured` output schema is enforced by the schema itself. Onboarding's "How to run locally" needed copyable command rows, so the prompt said "put the shell commands in a SINGLE fenced code block, one per line" — `openrouter/deepseek-v4-flash` (the registry default for the `onboarding` feature, `vendor/shared/contracts/platform.ts:47-51`) ignored it and wrote paragraphs with inline code, and the client's markdown-code-block parser silently rendered zero rows. Neither typecheck nor tests caught it: the parser legitimately returns null and the UI falls back to Markdown, so the section merely *looked* fine. Replacing the rule with a `commands: z.array(z.string()).nullish()` field on `OnboardingSection` made the SAME model populate it correctly on the first regenerate. Rule: if the UI derives STRUCTURE from model output, model it as a schema field, never as a markdown convention in `body`. The module now uses one shape for both non-prose outputs (`diagram`, `commands`): deterministic skeleton value → typed model field → post-validation confining it to its one legal `kind` with skeleton fallback. Corollary: also strip the duplicate from `body` in post-validation (a model that fills the field may ALSO still write the block, and the client renders both) — enforce it in code, not by asking the prompt again. Evidence: `src/modules/onboarding/generate.ts` (`mergeCommands`, `stripFencedBlocks`), `src/modules/onboarding/skeleton.ts` (`buildRunLocallyCommands`).
- **2026-07-18** — `MockGitClient.readFile` returns `''` for an unknown path and NEVER throws (`src/adapters/mocks.ts:293-295`), while the real `SimpleGitClient.readFile` throws (ENOENT, and now containment refusals) — any missing-/unreadable-file branch tested through the stock mock silently tests the wrong behavior (empty content instead of an error). Fix pattern: subclass the mock with a throwing `readFile` (see `CloneGitClient` in `test/reviews-context.it.test.ts`), or use the real adapter over a tmp-dir fixture with only `listFiles` stubbed (`RealFsGitClient` in `test/context.it.test.ts` — `readFile` is pure fs, no git CLI needed).
- **2026-07-29** — Building `UnifiedDiff` for `reviewPullRequest` by hand-assembling `{raw, files}` from TWO separately-stored fields is a trap: `eval/service.ts`'s `executeOneCase` originally set `files: (evalCase.inputFiles as UnifiedDiff['files'])` — but `input_files` is a plain `string[]` of touched paths (display-only, for the case editor's Files tab), NOT the shaped `{path, additions, deletions, hunks}[]` the citation-grounding gate needs. Every produced finding silently failed to ground against a real hunk, so every eval run scored 0 recall — caught only by a LIVE run against a real LLM (unit/integration tests used pre-shaped fixtures and never exercised this path). Fix: always re-derive `files` from the stored raw diff via `parseUnifiedDiff(evalCase.inputDiff)` (`src/adapters/git/diff-parser.ts`), never reconstruct `UnifiedDiff` from unrelated stored fields. Evidence: `src/modules/eval/service.ts` (`executeOneCase`).
- **2026-07-29** — A seed script that backfills a HISTORICAL snapshot (e.g. "version 1" config) must build it from the `seedAgents`/literal array item, never by re-`select()`ing the current `agents` row — the row may have been mutated (e.g. via the UI) since the agent was first seeded, in which case a backfill-from-current-row stamps the CURRENT edited state as the "original" version, permanently corrupting history. Caught live: edited an agent's system prompt via the UI (bumping it to v2), then ran a `pnpm db:seed` backfill that back-filled "v1" by re-reading the (by-then-already-edited) row — the Compare-runs system-prompt diff then showed "no visible change" between v1 and v2 because both snapshots held the same (already-edited) text. Evidence: `src/db/seed.ts` (the `agentVersions` backfill loop, uses `a.systemPrompt` etc. from the `seedAgents` literal, not `row.systemPrompt`).

- **2026-08-11** — A status derived from ONE half of the available evidence will eventually contradict the other half in the UI. `statusFromFindings(findingsCount)` mapped `0 → no_findings`, `>0 → succeeded` and never looked at the workflow run's own `conclusion` — so a CI run whose deterministic gate fired (findings at/above `ci_fail_on`, exit 1, **red** check on GitHub, merge blocked) was ingested as a green `succeeded` and rendered that way directly beside the "View job" link pointing at the failed job. Fixed with a THIRD state rather than by flipping to `failed`: `statusFromRun(findingsCount, conclusion)` yields `blocked` (gate fired — the feature working) as distinct from `failed` (runner/artifact broke). Rule for any status derived from an external system's run: if that system publishes its own outcome, the derived status must consume it, and "deliberately blocked" deserves its own value rather than being folded into either success or failure. Evidence: `src/modules/ci/helpers.ts` (`statusFromRun`), `src/modules/ci/ingest.ts`, `src/modules/ci/status.test.ts`.

## Codebase Patterns

- **2026-07-18** — `SimpleGitClient.readFile` enforces realpath containment (symlink escaping the clone → throw), and every current caller (`context/service.ts` preview+inventory, `reviews/run-executor.ts` injection, `conventions/content.ts`) deliberately maps a throw to "missing/unreadable" — a NEW caller passing user-influenced paths must wrap it in try/catch or a hostile git-tracked symlink becomes a 500. Testing note: realpath the CLONE-ROOT side too — macOS `os.tmpdir()` is itself a symlink (`/var/folders → /private/var`), so comparing against an unresolved root false-refuses every legit read in tmp fixtures. Evidence: `src/adapters/git/simple-git.ts` (readFile), `test/context.it.test.ts` (symlink test).
- **2026-07-18** — `contextRoots` (CONTEXT_ROOTS) gates ONLY the Project Context reader (inventory filter + preview 422 in `context/service.ts`); save-time validation (`normalizeContextDocuments`) and run-time injection (`run-executor.ts:loadProjectContext`) check only `isPathSafe`+`isMarkdownPath`. A path can be un-listable/un-previewable yet still attach and inject — documented behavior, pinned by `test/context-edges.it.test.ts` test (2); if product intent ever changes, that test will flag it.
- **2026-07-18** — `AgentsRepository.linkedSkills` selects the whole `skills` row, so a new `skills` column is immediately visible in `run-executor.ts` with zero agents-module read-path changes (this is how skill `context_documents` reached injection for free). Corollary for versioning: agent `context_documents` changes snapshot a version through a DEDICATED repo method (`setContextDocuments`), not through `isConfigChange`/`update` — there are now three snapshot writers funneling into `snapshotVersion` (insert, update, setContextDocuments); extend the version-bump rule in all of them or none. Evidence: `src/modules/agents/repository.ts`.
- **2026-07-18** — `schema.querystring` with a zod schema works fine under `fastify-type-provider-zod`; `context/routes.ts` (document preview `?path=`) is the first in-repo precedent — prior modules validated only `params`/`body`. Fastify decodes percent-encoding before the handler, so lexical path guards see the decoded form.
- **2026-07-18** — The `onboarding` tour's timestamp lives ONLY in the DB column (`onboarding.generated_at`, `defaultNow().notNull()` — `src/db/schema/context.ts:125`), never inside the persisted JSON payload: `buildSkeleton`/`generateOnboarding` leave `Onboarding.generated_at` null by design. So BOTH `OnboardingRepository.getTour` AND `upsertTour` must fold the column back into the parsed payload (helper `withGeneratedAt`, `.returning({generatedAt})` on the upsert) — miss either and every GET/recompute response carries `generated_at: null` and the client's "last refreshed" staleness header renders a placeholder. This class of bug shipped past THREE test layers (facts/generate unit tests never touch persistence; the it-test asserted only the DB column, not the response body; the client test fabricated the field on a mocked hook) and was caught only by plan-verifier + a live browser check. Any persisted-document contract whose canonical value is a DB column, not the JSON, has this shape. Evidence: `src/modules/onboarding/repository.ts`, `src/db/schema/context.ts:125`.
- **2026-07-15** — repo-intel's indexer only walks `.ts`/`.tsx`/`.js`/`.jsx`/`.mjs`/`.cjs` (`SUPPORTED_EXT`, `src/modules/repo-intel/constants.ts`) — no PHP, Vue SFCs, Python, Ruby, etc., regardless of how "full" the index status is. A PR whose changed files are all e.g. `.php`/`.vue` will show 0 symbols/0 callers everywhere `repoIntel.*` is consulted (Blast Radius, repo map, caller signatures) even on a cleanly-indexed repo — this is a language-coverage gap, not a stale/broken index. Verified live against a real synced Laravel+Vue repo (`IgorN/vue-starter-kit`): `repo_index_state.status: 'full'`, 34 symbols/38 files ranked, yet every `file_rank`/`symbols` row was a `.ts` file — zero `.php`/`.vue` entries. Evidence: `src/modules/repo-intel/constants.ts:14` (`SUPPORTED_EXT`), `src/modules/repo-intel/pipeline/walk.ts:101`.
- **2026-07-15** — `RepoIntelService.resyncRepo` (the ONLY manual re-index path, `POST /repos/:id/resync`) always advances the clone to `origin/<repo.defaultBranch>` before reindexing — never a PR's own branch/head. So repo-intel (and anything built on `getBlastRadius`/`getCallerSignatures`) can only ever reflect what already exists on the default branch. A PR that only ADDS new files/symbols will show 0 callers even right after a resync, by design — nothing on the indexed default branch can call code that doesn't exist there yet. This is expected (Blast Radius is meant for "did I break something that already exists," not "who might use my brand-new code"), but easy to mistake for a bug when testing against a real feature-branch PR. Evidence: `src/modules/repo-intel/service.ts:143-162`.
- **2026-07-15** — The seeded demo repo `acme/payments-api` (`db/seed.ts:24,77-89`, incl. PR #482 "Add rate limiting...") is a pure DB fixture — `repos.clonePath` is `null`, it has no real GitHub remote, and `resyncRepo`'s `no_clone` early-return (see entry above) makes any resync attempt a harmless no-op forever, not a transient/staleness state. Unlike `conventions`, which has an explicit `code_chunks`-based fallback for exactly this un-cloned-demo-repo case (see the entry below), repo-intel's own pipeline (`walk.ts`) has NO equivalent fallback — it only ever reads from `clonePath` on disk. So `acme/payments-api` structurally can never produce real Blast Radius / symbol / caller data; don't spend time trying to "fix" its index. Evidence: `src/db/seed.ts:77-89`, `src/modules/repo-intel/pipeline/walk.ts`.
- **2026-06-27** — `code_chunks` is NOT populated by the repo-intel indexer (grep: the only writer is the conventions seed). So the conventions extractor reads file content from the LOCAL GIT CLONE for any synced repo — `GitClient.listFiles` (new; `git ls-files`, honors .gitignore) + `git.readFile` — and falls back to `code_chunks` only for the un-cloned demo repo (seeded via `seed-conventions.ts`). A "synced" repo has `repos.clone_path` set; `repoIntel.getConventionSamples` needs `file_rank` (full index) which a merely-cloned repo lacks, so sampling falls back to a shallow-path heuristic. Trust boundary: the model returns a short DISTINCTIVE ANCHOR (rule name / identifier / config key) — NOT a multi-line snippet, because models paraphrase code (quotes, `;`, whitespace) so verbatim snippet-matching is flaky (a vue-starter-kit re-scan went 3→0). `verifyCandidates` locates the anchor (exact, then ws-normalized substring) and extracts the REAL surrounding lines as the snippet; anchor-not-found → dropped. This took verification from ~40% to ~95% of proposed candidates surviving. Evidence: `src/modules/conventions/{content,verify,extract}.ts`, `src/adapters/git/simple-git.ts`.
- **2026-06-26** — The Skills feature shipped MOST of its plumbing in the Part-0 starter BEFORE the lesson: the `skills`/`skill_versions`/`agent_skills` tables (`db/schema/skills.ts`, `agents.ts`), the `Skill`/`SkillType`/`SkillSource`/`AgentSkillLink` contracts, the agents-side link methods (`agentsRepo.linkedSkills/setSkills/linkSkill`), AND reviewer-core's prompt support (`PromptParts.skills` → `## Skills / rules` block). Only the **skills CRUD module + run-executor wiring + UI** were missing. Lesson: grep the schema/contracts before assuming a feature needs new tables. Evidence: `src/modules/skills/`, `src/db/schema/skills.ts`.
- **2026-06-26** — Wiring skills into a review run is one fetch in `run-executor.ts`: `this.agents.linkedSkills(agent.id)` → `.filter(l => l.skill.enabled).map(l => l.skill.body)` → pass as `skills` to `reviewPullRequest`. reviewer-core then populates `outcome.assembly.skills`, so the trace's skills block AND the token delta come for free. A DISABLED skill stays linked but is omitted — that omission is exactly the control-experiment lever (skill on vs off). Evidence: `src/modules/reviews/run-executor.ts` (~`:191`).
- **2026-07-29** — For a NEW module that owns its own tables (unlike `blast`/`why-risk-brief`, which piggyback on `ReviewRepository` and have no repository of their own), `routes.ts` must call ONLY `service.*`, never the module's `EvalRepository`/etc. directly — even for plain CRUD the service's primary orchestration methods don't already wrap. Confirmed by reading `skills/routes.ts` + `skills/service.ts` side by side (the other in-repo precedent for a module with its own repository): every route calls a thin `service` pass-through method, never `repo.*`. Add a thin wrapper method to the service rather than importing the repository into routes. Evidence: `src/modules/skills/{routes,service}.ts`, `src/modules/eval/{routes,service}.ts`.
- **2026-07-29** — Any NEW route that fans out to ≥1 LLM/model call per request needs an explicit `config: { rateLimit: {...} }` — this repo's global default (`app.ts`) is a generous per-IP bucket meant for cheap reads, and `POST /pulls/:id/review` already overrides it (`max: 10/min`) with the comment "each call can fan out to expensive LLM runs". A new route that fans out FURTHER (N cases per batch, or M agents × N cases for a "run all") inherits only the generous global bucket unless it explicitly sets a tighter `rateLimit`, too — easy to miss since nothing fails at build/test time. Evidence: `src/modules/reviews/routes.ts` (`POST /pulls/:id/review`), `src/modules/eval/routes.ts` (`POST /agents/:id/eval-runs`, `POST /eval-dashboard/run-all`).
- **2026-07-29** — A per-case-execution record shaped as ONE ARRAY ENTRY PER EXPECTATION ITEM (e.g. `EvalPerTrace[]`, one row per `must_find`/`must_not_flag` item plus one per unbacked "extra" finding) does NOT let a consumer recover "how many findings did this run actually produce" by counting or filtering the array — that count is a different, unrelated quantity (matched-must-find + confirmed-noise + extras) that isn't equal to `array.length` in general. If a client needs that raw count, expose it explicitly (this repo's fix: prepend one synthetic marker entry, e.g. `{name:'__produced_count__', actual:{produced: N}}`, so `array[0]` is a stable, unambiguous read) rather than asking every consumer to reverse-engineer it from the array's shape. Evidence: `src/modules/eval/service.ts` (`executeOneCase`'s `perTrace` construction).
- **2026-06-19** — `@devdigest/shared` contracts are vendored as TWO hand-maintained copies — `server/src/vendor/shared/` and `client/src/vendor/shared/` — resolved by tsconfig path alias, NOT auto-synced. Adding a field (e.g. `cost_usd`) means editing both in lock-step; the only intended diffs are comments. Evidence: `server/src/vendor/shared/contracts/trace.ts`, `platform.ts`.
- **2026-06-19** — `completeAgentRun`'s `values` shape is declared in TWO places that must match: the repo fn (`src/modules/reviews/repository/run.repo.ts`) AND the interface wrapper (`src/modules/reviews/repository.ts`). Adding a field (e.g. `costUsd`) to one without the other fails typecheck.
- **2026-06-19** — `RunTrace.stats` is assembled in TWO spots in `run-executor.ts` — the success path (~`:265`) AND the error/fallback trace (~`:425`). A new stats field (e.g. `cost_usd`) must be set in both. Evidence: `src/modules/reviews/run-executor.ts`.
- **2026-06-19** — PR-list COST is computed ON READ in `GET /repos/:id/pulls`, not denormalized: the SUM of ALL of a PR's `agent_runs.cost_usd` — `sql\`sum(${agentRuns.costUsd})\`` grouped by `pr_id` — i.e. "total spend to review this PR" (an earlier iteration surfaced only the latest review's run cost via leftJoin on `reviews.run_id`). Per-run cost still shows in the timeline/trace. Null (no priced run) → "—". Evidence: `src/modules/pulls/routes.ts`.
- **2026-06-19** — PR-list FINDINGS column data is computed on read in `GET /repos/:id/pulls`, unioning the LATEST review PER AGENT (not just the single newest review), so every agent that ran is represented while a re-run of an agent supersedes its older review — no stale/duplicate findings from the same agent. Dismissed findings are excluded (`isNull(findings.dismissedAt)`); dedup logic is the pure, unit-tested `latestReviewsPerAgent(reviewsNewestFirst)` in `status.ts` (key = `agentId ?? runId ?? id`). Counts come from `rollupSeverities` (also in `pulls/status.ts`) → `findings_critical/warning/suggestion`, plus a capped (`FINDINGS_PREVIEW_CAP`) `findings` preview embedded in `PrMeta` for the column's hover tooltip; findings-table `severity`/`category`/`kind` are `text`, so cast to the `Finding` enums when mapping. NOT handled (deliberately, learning system): cross-commit staleness (no per-review SHA in schema) and cross-agent semantic dedup. SCORE column still = the single newest review. Evidence: `src/modules/pulls/routes.ts`, `src/modules/pulls/status.ts`.
- **2026-07-12** — `ReviewRepository.reviewsForPull(prId)` returns `{review, findings}[]` already joined in ONE query — a more convenient source for "this PR's reviews with their findings" than `pulls/routes.ts`'s own two-query (reviews, then a separate findings-by-reviewId query) pattern. `latestReviewsPerAgent`'s generic constraint (`T extends {id, agentId, runId}`) is structural, so it works after a small `.map()` reshape with no second query needed. Evidence: `src/modules/smart-diff/service.ts` (`resolveFindingLines`) vs. `src/modules/pulls/routes.ts:134-194`.
- **2026-07-12** — `LocalNoAuthProvider.currentWorkspace()` always resolves the workspace literally named `'default'` (`db/seed.ts`'s `DEFAULT_WORKSPACE_NAME`), regardless of request contents (single-tenant MVP, no auth headers) — so an HTTP-level "cross-workspace 404" integration test needs no header/context manipulation, just seed the resource under a second, differently-named workspace and hit the route normally via `app.inject`. Evidence: `test/smart-diff.it.test.ts`.
- **2026-07-15** — `GET /pulls/:id/reviews` and `GET /pulls/:id/runs` take NO filter/pagination params (no severity/category/limit/cursor) — every review+finding for a PR comes back in one response, always. There's also no `GET /runs/:id` (run status by run-id alone — only PR-scoped `GET /pulls/:id/runs` / `/runs/active`) and no resolve-by-human-readable-name endpoint (`GET /repos?full_name=`, `GET /repos/:id/pulls?number=`) — every route param is an internal UUID (`IdParams`, `src/modules/_shared/schemas.ts`), resolved only by listing and filtering client-side. A new external consumer (e.g. `mcp-server/`) has to do that resolving/narrowing itself; closing this properly means adding those endpoints to `reviews`/`repos`/`pulls`. Evidence: `src/modules/reviews/{routes,service,repository}.ts`, `src/modules/pulls/routes.ts`.

## Tool & Library Notes

- **2026-07-15** — To force repo-intel to pick up LOCAL, uncommitted edits in an already-cloned repo's working tree (e.g. hand-testing Blast Radius against real code without pushing anything), `POST /repos/:id/resync` is the WRONG tool — `RepoIntelService.resyncRepo` → `container.git.sync` does `git fetch` + `git reset --hard origin/<branch>` (`src/adapters/git/simple-git.ts:77-88`), which wipes uncommitted changes back to the real remote. `service.refreshIndex(repoId)` (incremental) is ALSO a no-op on uncommitted changes — it short-circuits on `currentSha === lastIndexedSha` (`pipeline/incremental.ts:97`) and git SHA doesn't move without a real commit. What actually works: call `service.indexRepo(repoId)` (full reindex) directly — it unconditionally re-walks whatever is currently on disk in `clonePath`, no SHA check, no git calls at all. Build a throwaway script with `new Container(loadConfig(), (await createDb(url)).db)` → `new RepoIntelService(container)` → `.indexRepo(repoId)`. Verified: editing `resources/js/lib/utils.ts` + adding a new caller file in a real cloned repo (`IgorN/vue-starter-kit`), then `indexRepo`, produced genuinely-computed new `symbols`/`references` rows matching the edits — not fabricated. Evidence: `src/modules/repo-intel/service.ts:122-162`, `src/modules/repo-intel/pipeline/{full,incremental}.ts`.
- **2026-06-27** — The cheap extraction model (`openrouter/deepseek-v4-flash`) intermittently replies in CHINESE for an open-ended "extract rules" prompt — the system prompt MUST say "Respond in ENGLISH only" or half the candidates come back non-English. Also: a structured `completeStructured` call is non-deterministic even at `temperature:0` (one run proposed 4 / verified 0 with paraphrased snippets; the next proposed 5 / verified 5 verbatim) — so verification must tolerate minor reformatting (normalized-substring fallback) and the UI should show proposed-vs-verified counts. Evidence: `src/modules/conventions/extract.ts`.
- **2026-06-26** — The Skill editor's per-version "what changed" message needs a `message` column on `skill_versions` that the Part-0 schema did NOT have — added it (`db/schema/skills.ts` → `pnpm db:generate` → migration `0011_dapper_piledriver.sql` = `ALTER TABLE "skill_versions" ADD COLUMN "message" text` → `pnpm db:migrate` against the running Postgres). It's threaded only on a body change: `SkillsRepository.update(patch.versionMessage)` → `snapshotVersion(row, version, message)`. (The upstream lesson-2 branch added the same column as `0011_far_stryfe.sql` — same shape, different migration name.) Evidence: `src/modules/skills/repository.ts`, `src/db/migrations/0011_dapper_piledriver.sql`.
- **2026-06-26** — Skill import needs NO new deps: the upload is base64-in-JSON (`{filename, content_base64}`), not multipart, and the zip is read with a dependency-free reader over `node:zlib` (`src/modules/skills/unzip.ts`) that walks the central directory and decompresses ONLY the markdown core — executable/binary entries are listed but never inflated or run. Two gotchas baked in: (1) `Buffer.from(str,'base64')` NEVER throws (it silently drops bad chars) — validate the decoded length instead of try/catching it; (2) `inflateRawSync` needs `{ maxOutputLength }` + an `uncompressedSize` pre-check or a tiny archive is a heap-OOM zip bomb. Evidence: `src/modules/skills/{unzip,import,routes}.ts`.
- **2026-06-19** — New DB column flow: edit `db/schema/*.ts` → `pnpm db:generate` (drizzle-kit emits `00NN_*.sql` + `meta/00NN_snapshot.json`; needs NO DB connection) → `pnpm db:migrate` (NOT applied on boot; needs the DB). NEVER hand-author the SQL, even with Docker down — without the matching snapshot, the next `db:generate` re-emits the same column (a hand-authored 0010 was discarded and regenerated as `0010_clumsy_mulholland_black.sql` for exactly this reason). Evidence: `src/db/migrations/0010_clumsy_mulholland_black.sql`, `meta/_journal.json`.
- **2026-07-12** — `Container`'s `ContainerOverrides.llm: Partial<Record<'openai'|'anthropic'|'openrouter', LLMProvider>>` (`platform/container.ts`) accepts a pre-built provider double per id, bypassing secret lookup entirely. Injecting a double whose every method throws, then asserting a route still returns 200, is a concrete, deterministic, environment-independent proof that a route makes zero LLM calls — stronger than relying on the host machine's secrets file happening to be empty. Evidence: `test/smart-diff.it.test.ts`.
- **2026-07-18** — Integration tests do NOT have to live under `server/test/` — vitest `include` is `['test/**/*.test.ts','src/**/*.test.ts']`, so a `*.it.test.ts` colocated in `src/modules/<feature>/` is still picked up by the integration filter (`vitest run .it.test`) and excluded from the unit lane (`--exclude '**/*.it.test.ts'`) exactly like the `test/`-based ones. `onboarding.it.test.ts` is the first in-repo file to sit beside its module rather than in `test/`; a usable-index recompute test there needs BOTH `repo.clonePath` non-null AND a `full` RepoIntel double, because `resolveIndexState` (`onboarding/helpers.ts`) forces `degraded` whenever `hasClone` is false. Evidence: `server/vitest.config.ts`, `src/modules/onboarding/onboarding.it.test.ts`.

## Recurring Errors & Fixes

- **2026-07-30** — `createCaseFromFinding` (`EvalService`) used to ALWAYS insert a brand-new `eval_cases` row, one `must_find`/`must_not_flag` item each, with no check for an existing case on the same file. On a file with several distinct real findings (e.g. one controller with SQL injection + a hardcoded secret + mass assignment, all genuinely separate bugs), clicking "Turn into eval case" once per finding created N single-expectation cases that ALL shared the same frozen file — so at run time each case's OWN single expectation would match, but the agent's OTHER (also-real) findings on that same file always counted as unbacked "extra" noise, cratering precision for reasons that had nothing to do with the agent's actual quality; the SAME finding clicked twice created a literal duplicate case (no dedup at all). Fixed by having `createCaseFromFinding` search the agent's existing cases for one whose `input_diff` is BYTE-IDENTICAL to the newly-sliced diff (proof it's the same frozen file snapshot, so old expectations' line numbers stay meaningful) and, if found, APPEND the new expectation item to that case (skipping the append if an item with the same file/type/line-range already exists) instead of inserting a new case. Evidence: `src/modules/eval/service.ts` (`createCaseFromFinding`).
- **2026-07-30** — While testing the fix above, found `EvalRepository.listByOwner` has no `ORDER BY` — when several `eval_cases` rows share a byte-identical `input_diff` (pre-existing duplicates from before the merge fix landed), repeated calls to the SAME create-from-finding endpoint picked a DIFFERENT one of them as the merge target each time (confirmed empirically: 3 back-to-back calls returned 3 different case ids). Not dangerous by itself (case count never grew, and every candidate already carried the same expectation, so `alreadyPresent` correctly no-opped each time) but worth knowing: without an explicit ordering column (there's no `createdAt` on `eval_cases`), which specific duplicate "wins" a merge is arbitrary and can vary between requests. Actionable fix if this ever needs to be deterministic: add a `createdAt` timestamp column + `ORDER BY` (a new migration), or accept that duplicates are equivalent and only pick one to `latestRunForCase` off of them. This is now a non-issue GOING FORWARD since the merge fix prevents new duplicates from forming; it only ever bites on PRE-EXISTING duplicate data from before 2026-07-30. Evidence: `src/modules/eval/repository.ts` (`listByOwner`).

- **2026-07-18** — Integration tests that poll `agent_runs` to a terminal status then immediately `GET /runs/:id/trace` can 404 under parallel it-lane load: the success path calls `completeAgentRun` (terminal) BEFORE `saveRunTrace` (`run-executor.ts:304` vs `:354`). Deflake by retrying the trace fetch or polling `run_traces` instead of run status. Observed once in the full 15-container lane; green in isolation.

- **2026-08-11** — A Zod enum from `@devdigest/shared` RE-TYPED inline in a route's query schema is a silent drift point of the same family as the "declared in TWO places" entries above, but worse: it fails open. `ci/routes.ts` had `status: z.enum(['succeeded','failed','no_findings','running'])` hand-copied from the shared `CiRunStatus`, so adding a new value to the contract let it be written to the DB and rendered by the client while remaining **unfilterable through the API** — no typecheck error, no test failure, just a filter chip that silently matches nothing. Fix: import and use the shared schema (`status: CiRunStatus.optional()`); never re-spell a shared enum's members in a route. Evidence: `src/modules/ci/routes.ts` (`CiRunsQuery`), `src/vendor/shared/contracts/eval-ci.ts` (`CiRunStatus`).
