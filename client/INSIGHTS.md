## What Doesn't Work

- **2026-06-19** — Two separate `formatCost` implementations (in `RunCostBadge` and the trace-drawer `helpers.ts`) drifted: the badge used `toExponential` for `< $0.001`, so the timeline showed an unreadable "$7.3e-4" while the trace tile showed "$0.0007". Fixed by extracting ONE `formatCost` to `src/lib/cost.ts` consumed by both. Lesson: a display formatter used in >1 place belongs in a shared module from the start. Evidence: `client/src/lib/cost.ts`.
- **2026-06-19** — A hover popover positioned `absolute` inside the PR-list table got clipped by the table card's `overflow: hidden`, and a `top: 100% + gap` offset made it close before you could reach it (the pointer crosses empty space → `onMouseLeave` fires). Fix: render the popover `position: fixed` anchored via `getBoundingClientRect` (escapes the `overflow:hidden` ancestor) + a ~160ms close delay that the popover's own `onMouseEnter` cancels, so the pointer can travel onto it and scroll. Evidence: `client/src/components/FindingsSummary/FindingsSummary.tsx`.

- **2026-07-18** — A viewport-geometry scroll-spy is the WRONG tool for a page whose sections are MODEL-GENERATED: their count, height and content are unknown at design time, so any "which section is active" heuristic is tuned against one repo's layout and misbehaves on the next. Onboarding's "On this page" ToC went through two, each shipping a DIFFERENT wrong highlight: (1) a reading-line threshold (`rect.top <= 140`) meant the trailing sections could never activate — at the end of the page there is no scroll room left for them to cross the line, so "Guided reading path" was unreachable; (2) largest-visible-area let one tall section (architecture + its Mermaid diagram) starve every short one, so the small "Critical paths" never won. Adding an end-of-scroll override to (1) just made it skip a section instead. Settled on EXPLICIT SELECTION ONLY: the active entry is parent state (`OnboardingView.selectedKind`) set by a ToC click or a section-header click (`SectionCard.onActivate`) — which deleted every effect, ref, listener and rAF from `TableOfContents` (128 → 58 lines) and has no edge cases. Do not "fix" this back into a scroll-spy without new information. Evidence: `.../OnboardingView/TableOfContents.tsx` (the rationale is in its header comment), `.../OnboardingView/OnboardingView.tsx`.
- **2026-07-18** — The two ContextTab mutations (`useSetAgentContextDocuments`/`useSetSkillContextDocuments`) are fire-and-forget: components call `.mutate(next)` with no `onError` and never read mutation state, so a FAILED attach/reorder POST is invisible — the optimistic local order persists until the parent query refetch resets it. No AC required an error path, but future implementers should add one before test-writers go looking for it (there is nothing to assert today). Evidence: `app/agents/[id]/.../ContextTab/ContextTab.tsx`, `lib/hooks/context.ts`.
- **2026-07-29** — The 2026-06-19 "two vendored copies" entry below undersold the risk: `client/src/vendor/shared/contracts/knowledge.ts` was found LIVE to be missing `AgentVersionConfig`/`AgentVersion` entirely (both present in the server copy since an earlier lesson) — not a field-level drift but a whole-type gap, undetected until a new hook (`useAgentVersion`) needed it and `pnpm typecheck` had nothing to catch (the client simply never imported the missing type before). Before assuming ANY type exists in `@devdigest/shared` client-side, diff the two `contracts/*.ts` files directly rather than trusting that "it's probably synced." Evidence: `client/src/vendor/shared/contracts/knowledge.ts` vs the server copy.
- **2026-07-29** — `@devdigest/ui`'s `Modal` (`src/vendor/ui/kit/Modal.tsx`) backdrop is `rgba(0,0,0,0.5)` — on a page section with BUSY, LIGHT-colored text behind it (e.g. a list of `FindingCard`s), that text stays clearly legible through the dim, which at a glance looks exactly like a broken/missing backdrop (a z-index or stacking-context bug). It is NOT one: `document.elementFromPoint` at multiple coordinates confirmed the modal's own dialog/backdrop is genuinely topmost and interactive; a 50%-black overlay on an already-dark theme just doesn't dim light text much. Don't chase this as a stacking bug — verify with `elementFromPoint` before concluding the backdrop is broken. Evidence: `EvalCaseEditor` opened from `FindingCard`, `src/vendor/ui/kit/Modal.tsx`.
- **2026-07-30 (supersedes the 2026-07-29 entry above for THIS specific case)** — The "text bleeds through the modal" report recurred from a real user, and this time it WAS a real bug, just not a stacking bug: `FindingCard.tsx` rendered `<EvalCaseEditor>` as a DESCENDANT of the card's own root `<div style={s.card(..., muted)}>`, and `s.card` sets `opacity: muted ? 0.6 : 1`. "Turn into eval case" is only ever clickable once the finding is `muted` (accepted/dismissed) — so the modal ALWAYS opened already nested inside an opacity:0.6 ancestor, making its own fully-opaque `background: var(--bg-elevated)` panel render at 60% opacity and let the page behind visibly interleave with the modal's own text. CSS `opacity` applies to a `position: fixed` descendant's compositing, not just its layout — `position: fixed` does NOT escape an ancestor's opacity the way it escapes `overflow: hidden` clipping. Diagnosed by walking `getComputedStyle` up from `document.querySelector('[role="dialog"]')`'s parent chain in a live browser (found `opacity: "0.6"` one level up) rather than re-trusting the earlier "just contrast" conclusion. Fix: render the modal as a SIBLING of the card's root div (wrap the component return in a Fragment) so it never inherits the card's dimming. General lesson: a conditionally-rendered modal/portal-like element must not be nested inside ANY ancestor that gets `opacity`/`filter`/`transform` applied conditionally — check the ACTUAL trigger condition (here, `muted` is always true when the button is clickable) before concluding a one-off visual bug is cosmetic. Evidence: `app/repos/[repoId]/pulls/[number]/_components/FindingCard/FindingCard.tsx`, `FindingCard/styles.ts:16`.

- **2026-08-03** — An element that is BOTH a grid item and a flex container defaults to `min-height: auto` on both counts, so it grows to fit its content instead of shrinking to its track — and a child with `flex: 1; overflow: auto` then never has anything to scroll. The Export-to-CI wizard's preview pane looked "cut off with no scrollbar": `previewWrap` (grid, `height: 340`, `overflow: hidden`) had a `pane` child that silently exceeded 340px, and the wrapper's `overflow: hidden` just clipped it. Fix: `minHeight: 0` on EVERY scrollable descendant in the chain (the grid items AND the `flex: 1` children), not only the one with `overflow: auto`. Invisible to `pnpm typecheck` and to RTL (jsdom does no layout) — the only reliable check is measuring `scrollHeight > clientHeight` in a real browser. Related but a different mechanism: the 2026-07-30 `opacity` entry above (a `position: fixed` descendant escapes `overflow: hidden` clipping but NOT an ancestor's `opacity`). Evidence: `app/agents/[id]/.../CITab/_components/ExportWizard/styles.ts` (`previewWrap`/`tree`/`pane`/`paneBody`).
- **2026-08-03** — An empty state that REPLACES the whole page can hide the only control capable of populating it. `/ci-runs` rendered `<EmptyState>` instead of the header whenever `runs.length === 0`, but the header held the **Refresh** button — the sole GitHub-pull/ingest trigger. Result was a closed loop: no rows ⇒ no button ⇒ no rows, with two ingestable artifacts already sitting in GitHub and no way to reach them from the UI. The design's empty screen legitimately replaced the page, but the design had no Refresh-driven ingest to strand — copying its structure imported a deadlock that didn't exist in the mockup. Rule: before letting an empty state replace a page, check whether any control it removes is the one that ends the empty state. Evidence: `app/ci-runs/_components/CiRunsView/CiRunsView.tsx`.

## Tool & Library Notes

- **2026-07-12** — This project's client test suite has ZERO `userEvent` usage anywhere and `@testing-library/user-event` isn't installed (`client/package.json`) — every existing interaction test (`SeverityFilter.test.tsx`, `FindingCard.test.tsx`, `RunTraceDrawer.test.tsx`, `FindingsSummary.test.tsx`) uses `fireEvent` from `@testing-library/react` exclusively. The generic `react-testing-library` skill's own template defaults to `userEvent` — following that default verbatim here hits a module-resolution error.
- **2026-07-18** — To vary a `vi.mock`ed hook's return per test, use a `vi.hoisted(() => ({holder}))` object read by the mock factory; and never call `mockX.mockReturnValue(...)` INSIDE a shared render helper — it silently overrides any `mockImplementation` a test set before calling the helper (last-configured wins). Pass per-test behavior INTO the helper instead. Evidence: `RunTraceDrawer.test.tsx` (`vi.hoisted`), `AgentEditor/.../ContextTab.test.tsx` (`renderTab(agent, previewImpl?)`).
- **2026-07-12** — jsdom 25 (this project's pinned version) does NOT implement `Element.prototype.scrollIntoView`, and `client/src/test/setup.ts` has no polyfill — any component calling `.scrollIntoView(...)` under test must optional-chain it (`el?.scrollIntoView?.(...)`) or the test throws. Separately, jsdom's CSSOM round-trips `var(--custom-property)` tokens through shorthand style properties (`background`, `boxShadow`) losslessly via direct `element.style.<prop>` access — a reliable, mock-free way to assert CSS-variable-driven visual states (highlight/active/etc.) in this codebase's all-inline-style convention. Evidence: `client/src/components/diff-viewer/FileCard/FileCard.tsx`, `client/src/test/setup.ts`.
- **2026-07-18** — `src/lib/hooks/` had ZERO hook tests before Onboarding (every client `*.test.tsx` was a component test; no `renderHook` usage existed anywhere). The working harness for a TanStack Query hook: `renderHook(() => useX(), { wrapper })` where `wrapper` mounts a `QueryClientProvider` built with `new QueryClient({ defaultOptions: { queries: { retry: false } } })`, mocking the single I/O seam `@/lib/api` (`../api`) via `vi.mock` rather than `fetch` (msw is NOT installed). Assert cache writes with `queryClient.getQueryData(key)`. Evidence: `src/lib/hooks/onboarding.test.tsx`.

## Recurring Errors & Fixes

- **2026-07-30** — `FindingCard`'s card style (`styles.ts`'s `card()`) set `borderColor` (a shorthand that covers all 4 sides, including left) AND `borderLeftColor` in the same style object, to give an accent-colored left edge while `borderColor` covers top/right/bottom — a prior comment claimed this was "all-longhand" (it isn't: `borderColor` ≠ `border`, but React still treats it as overlapping `borderLeftColor`) and React logs `Updating a style property during rerender (borderColor) when a conflicting property is set (borderLeftColor)...` on every accept/dismiss toggle (any rerender that changes `focused`/`sevColor`). Fix: use fully-disjoint longhands — `borderTopColor`/`borderRightColor`/`borderBottomColor` for the reactive (`focused`) color, `borderLeftColor` for the static accent — never combine `borderColor` with any single-side `border*Color`. Evidence: `FindingCard/styles.ts`'s `card()`.

- **2026-06-19** — Adding a required field to a vendored Zod contract breaks test fixtures that build the full type from a `Partial<>` helper: `TS2719: Two different types with this name exist… 'undefined' is not assignable`. Fix: add the new field (e.g. `cost_usd: null`) to the helper's base object. Evidence: `client/src/app/repos/[repoId]/pulls/[number]/_components/RunHistory/RunHistory.test.tsx`.
- **2026-07-29** — `src/vendor/ui/charts/Sparkline.tsx` divided by `data.length - 1` to place points along the x-axis; a single-point series (an agent/case with exactly 1 eval-run batch) made that `0/0 = NaN`, which React logs as `Received NaN for the \`cx\` attribute` and which Next's dev overlay renders as a full-screen blocking error — easy to misread as "the sparkline feature is missing/broken" when it's actually just this one-point edge case. Fix: use `data.length > 1 ? data.length - 1 : 1` as the denominator. Always test chart components against a 1-point series, not just 0 and N. Evidence: `src/vendor/ui/charts/Sparkline.tsx:19`.
- **2026-07-29** — Both "recent runs" tables (`EvalDashboardIndex`'s workspace-wide table AND `EvalAgentDrillIn`'s per-agent table) initially rendered Recall/Precision/Citation as plain percentage text — the reference design shows each as a value PLUS a thin colored fill bar underneath (same accent/ok/warn per-metric color scheme as the tiles/chart), and its absence read as "the table has no color at all" even though the PASS column's color (`passRateColor`) was already correct. No existing `@devdigest/ui` component fit (the pre-existing `BarRow` is a fixed 3-column label+bar+suffix layout meant for a standalone list, not a narrow grid table cell) — added a new minimal `src/vendor/ui/charts/MetricBarCell.tsx` (value + 4px fill bar, no label) and reused it in both tables' row renderers. Evidence: `EvalDashboardIndex.tsx` (`RunRow`), `EvalAgentDrillIn.tsx` (`RunRow`), `src/vendor/ui/charts/MetricBarCell.tsx`.
- **2026-07-29** — `EvalAgentDrillIn`'s metric tiles (Recall/Precision/Citation) initially shipped with NO trend sparkline at all — a plain custom `MetricTile`, not the shared `@devdigest/ui` `MetricCard` that already supports a `trend` prop — even though the source design showed one per tile. Separately, `toChartSeries` (same folder's `helpers.ts`, feeds the big `LineChart` below the tiles) had recall and precision's colors swapped (`--ok`/green on recall, `--accent`/blue on precision) versus the design, where recall is blue and precision is green. Fixed by adding `tileTrend(trend, key)` + rendering a `Sparkline` per tile with `color` matching the (corrected) `toChartSeries` mapping: recall=`--accent`, precision=`--ok`, citation=`--warn`. Lesson: when a design reference shows a decorative-looking element (a mini trend line in a tile corner), verify it's actually implemented — it's easy to skip as "just decoration" — and check series colors against the reference pixel-by-pixel, not just presence/absence of a chart. Evidence: `app/eval/[agentId]/_components/EvalAgentDrillIn/EvalAgentDrillIn.tsx`, `.../helpers.ts`.

- **2026-08-03** — A design mockup's PLACEHOLDER TEXT copied verbatim into a `<select>`'s empty option reads as an already-selected real value. The Export wizard's repo picker used `repoPlaceholder: "acme/payments-api"` (the mockup's sample repo) as the label of the `value: ""` option, so a user opening the wizard saw what looked like a pre-filled target repository and reported the update flow as "not prefilled" when in fact nothing was selected at all.
